## F3 — Migração Agno 3.x

Itens detalhados em [F3-migracao-agno.md](F3-migracao-agno.md) (alvo: 3.1.12). Contexto original:

Bump para 3.1.x só no `AgnoRuntime` (renomes: `enable_user_memories`→`update_memory_on_run`, `Knowledge.add_content`→`insert`, `JWTMiddleware(verification_keys)`, `mcp_server=`); `MigrationManager` para a tabela `agno_runs`; testes de contrato na matriz 2.5.8 × 3.1.x durante a transição; runbook com backup do Mongo; **nunca** rodar `cleanup_legacy_runs_column` no mesmo release. Conferir o controle de telemetria dos evals no Agno 3.x (no 2.5.8 a rota `/eval-runs` cria evals com `telemetry=True` que ignoram `AGNO_TELEMETRY`; resíduo do F1-03). Resíduos do F2-08 a rever no upgrade: (1) o `SessionDb` sobrescreve `get_session` para consultar sem o filtro de `session_type` (decisão do usuário: um team que reusa o `session_id` de um agente mantém o histórico, como no `MongoDb` síncrono; o `AsyncMongoDb` do 2.5.8 filtra por tipo e sobrescreveria o documento): conferir a semântica do 3.x e manter ou remover a sobrescrita; (2) o db de sessões usa o motor (`AsyncIOMotorClient`), porque no 2.5.8 o `AsyncMongoDb` não funciona com o `AsyncMongoClient` do pymongo 4.18 (detecção por `pymongo.collection.AsyncCollection`, `aggregate(...).to_list` e `close` sem `await`); o motor tem fim de vida anunciado: migrar para o `AsyncMongoClient` quando o agno suportar e consolidar os clientes motor (container, `MongoClientFactory`, sessões); (3) `POST /databases/all/migrate` responde 207 com Mongo (assinatura de `get_latest_schema_version` do agno 2.5.8, igual no `MongoDb` síncrono): conferir no 3.x junto com o `MigrationManager`. Resíduos do F2-11 a rever no upgrade: o RAG semântico depende de internos do `agno.vectordb.mongodb.MongoDb` 2.5.8 (`_get_collection` protegido, no reparo e no descarte; `_create_search_index` protegido, substituído pelo `GuardedMongoVectorDb` porque o agno o chama em `_get_or_create_collection` lendo `embedder.dimensions`; `collection_exists`; `prepare_doc` como caminho comum de `insert`/`upsert`/`async_insert`/`async_upsert`, onde fica a guarda, com o agno engolindo o `ValueError` por documento); o `OllamaEmbedder` assume `dimensions=4096` e devolve `[]` para vetor de outro tamanho (a sonda chama `embedder.client.embed(model, input)` do ollama 0.6.3 sem `dimensions`); semântica de `dimensions` por embedder (só pedido ao provider em OpenAI text-embedding-3/base_url, OpenAI-compatível, Azure — `None` não pede, o ada-002 recusa — e Gemini `output_dimensionality`; pedido e filtro no Ollama): revalidar numa matriz de versões com os testes live de `tests/integration/test_f2_11_rag_live.py`.

## F4 — Tools + MCP cliente

Antecipado no FA-06: guarda SSRF na `route`/`base_url` gravadas pela API Admin e headers de tool por referência. Continua aqui o resto (DNS rebinding, redirect dos SDKs, `AsyncClient` compartilhado, limites, retry).

Decisão: sem porta `ToolSource` (uma implementação só, a HTTP; reavaliar no F4-02 com o MCP como segunda fonte). Resíduos do F4-01: `base_url` da config no `azure` segue recusada (endpoint por recurso, sem host padrão, e o `AzureOpenAIEmbedder` precisaria da mesma subclasse dos dois caminhos; habilitar com o cliente guardado é item próprio); `MODEL_BASE_URL_ALLOWLIST` por provider não feita; sem `base_url` da config o SDK usa o cliente padrão (redirect seguido no host do próprio provider ou do operador: destino confiável; `gemini`/`anthropic` não aceitam `base_url`); os clientes httpx globais do agno (`agno/utils/http.py`) não são usados pelos providers built-in no agno 3.1.12; timeout/limite/retry das tools fixos no código (sem variável de ambiente). ## F9 — Execução durável

`QueueConfig(durable=True)` (exige `db=`), runs em background com cancelamento/deduplicação, runbook, teste de caos (processo morto no meio do run).
Pendências de cancelamento herdadas do F1-10 (comportamento do agno 2.5.8, igual com o gerenciador stock; eram xfail estritos em `tests/security/test_qa_f1_10_cancel.py`, removidos no F3-05 porque as duas primeiras deixaram de valer no agno 3.1.12, ver o fim desta nota): cancelar o run de um team não cancela o run do membro em andamento, que segue consumindo o modelo até o fim (BUG-F110-TEAM-CANCEL-MEMBER); o run de membro cancelado diretamente fica no gerenciador de cancelamento para sempre, pois o caminho de delegação não faz cleanup (BUG-F110-MEMBER-CANCEL-LEAK); entrada órfã quando um run de background é registrado e o Mongo falha antes do `_arun` (o cleanup fica no `finally` do `_arun`); colisão de `run_id` em dois pedidos AG-UI simultâneos (o F1-10 só troca o `runId` já registrado); dono do run (qualquer chave run cancela um run em andamento cujo id conheça, ver F5-02). Observação do F2-08: com `db=` no AgentOS o xfail BUG-F110-MEMBER-CANCEL-LEAK fica intermitente (o run do membro cancelado às vezes é limpo); reavaliar com o db presente. Cancelamento propagado aos membros, TTL/limpeza das entradas e `run_id` gerado pelo servidor entram com a execução durável. F3-05 (agno 3.1.12): os dois xfail estritos saíram (viraram XPASS): cancelar o run do team cancela o do membro (cascata do agno) e o run de membro cancelado não fica no gerenciador; e cancelar o run do membro agora encerra o team como cancelado (`test_cancel_do_run_do_membro_encerra_o_team_como_cancelado`). O `RegisteredRunCancellationManager` não implementa o `register_member_run` (no-op da ABC do 3.x): a cascata funciona sem ele nesses testes; reavaliar com a execução durável. Continuam pendentes: entrada órfã do background, colisão de `runId` simultâneo no AG-UI e dono do run (F5-02). Novo do 3.x: o `run_id` vindo do cliente (form REST, `runId` do AG-UI) é a chave do documento em `agno_runs`; o `SessionDb` recusa regravar run de outra sessão ou de outro `user_id` (filtro com o dono e índice único de `run_id`: quem grava primeiro fica com o id) e o AG-UI troca o `runId` já gravado por um UUID4, mas a rota REST do agno ainda roda o run sem gravá-lo e dois primeiros runs simultâneos com o mesmo `run_id` disputam a inserção (o segundo não é gravado): os dois casos ficam para o `run_id` gerado pelo servidor.
